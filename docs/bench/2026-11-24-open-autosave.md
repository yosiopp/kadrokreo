# 計測（2026-11-24、kdr を開く時間の内訳と自動保存）

`npm run bench` の結果（`bench/out/latest.md` をそのまま写したもの）と、Chrome の CPU プロファイルで見た内訳。値は操作 1 回ぶんのメインスレッドの時間（ms）。測り方は `bench/run.mjs` と `cli/bench/` の先頭のコメント。
その前の移り変わりは `2026-11-24-store-preview.md`・`2026-11-22-perf-rest-3.md`・`2026-11-22-perf-rest-2.md`・`2026-11-22-perf-rest.md`・`2026-11-22.md`・`2026-11-22-kdr-tar.md`。

- 環境: darwin arm64、Node v24、Chrome（ヘッドレス）、1440×900、deviceScaleFactor 2。同じマシンで続けて測った（並行して別の処理も動いていたので、値は揺れる）
- 直す前は直前の main（bench は同じもの）で測った。今回の変更は kdr を開く道を通らないので、「kdr を開く」などの行の前後の差は揺れ

## large を開くときの内訳（editor、CPU プロファイル）

圧縮しないビルド（`vite build --minify false`）を `vite preview` で配り、ファイルを渡してから描画が終わるまでの CPU プロファイル（0.1ms ごと）を 3 回取って見た値。

| 中身 | 時間（ms） | 見たこと |
| --- | ---: | --- |
| 展開・JSON の解析・検証（`decodeKdr`） | 約 21 | うち検証（`parseNode` など）約 15。項目ごとの確かめそのもので、弱めない |
| パネルの組み立て（React） | 約 13〜17 | レイヤーの一覧の元の集め直し・木の並べ、見えている行の位置を測るときのレイアウト |
| 最初の描画（`renderScene` と取っておく絵への写し） | 約 80 | 下の 3 つと、図形ごとの save / restore・塗り |
| そのうちテキストの行分け（`layoutText`） | 約 20 | ほとんどが `measureText`。下の「見送ったもの」 |
| そのうち描いた絵を取っておく写し（`drawImage`） | 約 13 | ここで描いた命令がまとめて実行される（描く量そのもの） |
| 開いて 0.5 秒後の自動保存（開く時間には入らない） | 約 23〜28 | IndexedDB の `put` がドキュメント全体をその場で写す時間 |

- issue に書いていた「行分け約 19ms」は合っていたが、プロファイルを取り始めた直後には、ファイルを渡す前の最初の描画で書体の準備に 300ms ほどかかる回があり、それが混ざると値が大きく出る。ページを開いてから 2.5 秒待って測った。

## 自動保存（CPU プロファイル）

開いて 0.5 秒後の自動保存で、メインスレッドが続けて止まった時間（`saveDocument` と、そこから続く書き込みのタスク）。3 回ずつ。

| | 直す前 | 直した後 |
| --- | --- | --- |
| large（ノード 17,057） | 1 タスク 23〜28ms | 約 20 タスク、最長 4〜5ms（合計 21〜22ms） |
| photos（一辺 1024px の画像 24 枚） | 1 タスク 13〜17ms | 25 タスク、最長 1.4ms 以下（合計 10〜12ms） |

- ノードの表を 1,000 個ずつに分けて別のレコードにし、画像も 1 枚ずつ、1 つのトランザクションの中で前のものが書けてから次を書く（成功の知らせは別のタスクで来るので、その間に描画や入力の処理が挟まる）。最初のタスクに残るのは、使っていない画像を除く確かめ（約 2.4ms）と、ページの表を空にしたドキュメントの書き込み。

## 見送ったもの

- テキストの行分け: 段落がまるごと幅に収まるときに 1 回だけ測る近道を試したが、時間は変わらなかった（`measureText` は呼ぶ回数より、初めて見る文字列の形を作る分が重い。描くときの `fillText` はその結果を使い回す）。
  減らすには、画面上でごく小さく描かれる文字（large の全体表示は 5% で、文字は 1〜2px）を行分けせず帯などで描くことになり、見た目を変えるので別に考える。
- 自動保存を操作のない時間（`requestIdleCallback`）に回す案: 開いた直後にパンし続けても、パンの合間に空き時間があるので保存はその最中に入り、止まる時間も変わらなかった。
- 開いた kdr のファイル（Blob）をそのまま保存して写さずに済ませる案: 保存データの形が変わり、読み直すときに毎回展開と検証が要る。分けて書くほうが、形を大きく変えずに済む。
- 検証の高速化: 項目ごとのパスの文字列を作らずに済ませるには確かめの関数の形を全部変えることになり、見込める差（数 ms）に比べて手間が大きい。
