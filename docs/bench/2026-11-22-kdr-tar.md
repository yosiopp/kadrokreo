# kdr を tar.gz にした前後（2026-11-22）

kdr を tar.gz にして画像を切り出す変更（kdr v16）の前後に、同じマシンで続けて `npm run bench` を流した結果。
値は操作 1 回ぶんのメインスレッドの時間（ms）、メモリの行だけ MB。測り方は `bench/run.mjs` と `cli/bench/` の先頭のコメント。

- 環境: darwin arm64、Node v24.16.0、Chrome（ヘッドレス）、1440×900、deviceScaleFactor 2
- 前: `c9e89ae`（kdr v15・パスの曲線・SVG の取り込み）に計測の追加（photos・メモリ）だけを入れたもの。後: v16 を入れたもの
- メモリの 2 行は、`cli/bench/memory.ts` の GC を 1 回から 4 回に直したあと、両方を `memory.ts` だけ 3 回ずつ測り直した中央値に差し替えた
  （GC 1 回だと、ストリームの後始末が残って「残るメモリ」が 0 や負になることがあった）。
- ブラウザの「JS ヒープの増分」は ArrayBuffer の中身や大きな文字列が入らないので、メモリは Node の値で比べる。

## まとめ

| | 前 | 後 |
| --- | ---: | ---: |
| photos（画像 24 枚・72MB）: Node で kdr を読む | 696ms | 73ms |
| photos: 読む途中の最大メモリの増分 | 405MB | 90MB |
| photos: 読んだあとに残るメモリ | 93MB（base64 の文字列） | 69MB（画像のバイト列そのもの） |
| photos: kdr を開く（editor / viewer のメインスレッド） | 809ms / 773ms | 73ms / 86ms |
| large（画像は 32px が 50 枚）: Node で kdr を読む | 25ms | 30ms |
| large: kdr を開く（editor / viewer） | 694ms / 342ms | 693ms / 309ms |

画像が重いほど効く（base64 の文字列を作らず、JSON の解析と `atob` に画像を通さない）。画像がほとんどないデザインでは、
tar を読む手間の分だけ Node での読み込みが数 ms 遅く、途中のメモリも large で 15MB ほど多い（ブラウザで開く時間は変わらないか速い）。
